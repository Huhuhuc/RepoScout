# RepoScout：简历与面试说明

## 项目定位

RepoScout 是面向开源项目选型的单 Agent 调研工具。输入候选仓库和条件，读取 GitHub 原文，由模型调用受控工具，形成“支持 / 不支持 / 未知 / 冲突”的比较矩阵，并保留来源和操作记录。当前为本地单用户原型。

## 60 秒讲解

我做这个项目是为了解决直接问大模型选型时，结论难核查、版本限制容易被忽略的问题。系统把需求、来源、证据与判断分开保存，模型负责决定读哪些资料和如何判断；程序控制网络范围、参数合法性、原文引用、调用预算和最终提交。简单问题先用 README 快速核查，证据缺口再进入文档与 Issue 调查。异常时保存检查点，用户可继续调查。项目包含冻结资料对照、成本统计和 Windows/Linux CI。它没有解决所有语义错误，实验中的失败案例也被保留。

## 可以写进简历的内容

- 基于 Python、FastAPI、SQLite 构建开源选型 Agent，接入 DeepSeek 工具调用，覆盖 GitHub README、仓库文档、Release 与 Issue 采集，输出可追溯比较矩阵。
- 实现自动 / 深入两种调查策略、证据缺口补查、请求与 Token 预算控制、异常部分报告及检查点恢复；通过服务端原文片段截取减少模型复制 Markdown 引用时的格式错误。
- 建立三个真实仓库、12 条固定资料任务的四策略对照，记录判断、引用、有效提交、Token 与耗时；工程测试和跨平台 CI 结果以收尾验收记录为准。

以上描述区分系统能力与实验覆盖：真实评测集当前主要是 README 与仓库文档，不代表已经全面评测 Release、Issue 或多版本冲突。数字只能引用实际保存的结果；不要写“企业级”“准确率 100%”“稳定降低成本”。

## 主要面试问题

**为什么不把所有资料一次交给模型？**

资料已整理且体量小的情况下，单次回答可能更便宜，甚至效果更好。Agent 的目标是按需获取缺失资料、处理限制和记录过程；是否值得更多调用需要用同资料对照说明，不能预设 Agent 一定更好。

**什么是 Agent 的自主性，哪些部分是程序规则？**

模型选择允许的工具、查询和判断；程序负责限定预算、网络和工具参数，检查报告完整性及引用关系。它是一个受约束的工具循环，不是每一步都写死，也不是无限循环。

**如何防止幻觉？**

避免把无资料当成不支持，要求确定性判断关联原文；引用必须来自同一仓库和条件。片段编号由服务端还原原文，保证内容确实存在。语义支持仍可能出错，可选复核只用同一模型的独立提示，不等于独立事实核验。

**为什么保留 unknown？**

未知是有效调查结论。搜索不到资料与功能不存在不同；强行给出支持或不支持会增加误导。有效的 unknown 报告也需要正常提交，预算耗尽的部分报告单独统计。

**恢复任务为什么创建新 ID？**

原任务保留用于审计，新任务复用已存来源、证据和矩阵并分配新预算。恢复不会把旧任务变成成功，也不会继续沿用已补查却未复核的旧判断。用户能区分两次运行的成本。

**为什么没有直接用 LangGraph？**

当前单 Agent 流程较小，显式 Python 状态控制更便于展示预算、停止和恢复逻辑。使用框架不是质量指标；复杂分支、人工审批和分布式任务增加时，再评估迁移成本。

**评测有哪些限制？**

固定资料提供可复现的检索池，不反映实时搜索的全部难度；单次运行无法估计稳定性。人工预设证据片段的匹配评分可能漏掉其他合理引用，需分开报告状态正确性、严格引用匹配和完成率。基线直接得到全部资料，Agent 按需检索；对比的是整体流程，并非纯推理能力。关闭定向补查仍允许其他读取工具。

## 下一阶段边界

当前可作为实习作品展示。后续候选发现排序、维护者评论与关联 PR、多版本冲突、向量检索、多用户隔离和公网部署都属于额外范围。完成此轮验收后，应优先制作新的 AI＋游戏作品，避免无限增加平台功能。
